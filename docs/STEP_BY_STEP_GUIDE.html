Document Management System

A complete, no-jargon walkthrough: from starting the system, creating a customer (tenant), attaching AWS / MinIO / Google / Azure storage, to uploading and downloading files with the APIs.

Written for first-time users on Windows. You can open this file in a browser and print it to PDF (Ctrl+P → Save as PDF) or open it in Microsoft Word.

What this system is (in plain words)

Think of this product as a filing cabinet in the cloud, but the cabinet can live in different warehouses:

  • AWS S3 — Amazon’s warehouse
  • MinIO — a warehouse you can run on your own computer (best for learning)
  • Google Cloud Storage — Google’s warehouse
  • Azure Blob Storage — Microsoft’s warehouse

Important ideas:

WordMeaning
TenantOne customer / company. Example: Acme Corp. Their files never mix with another company.
AdminThe person who creates tenants and points each tenant at a warehouse.
UserAn employee of that company who uploads and downloads documents.
APIA web address the computer talks to. You can also click the same actions in Swagger (a web form).
HeaderA small name-tag sent with every request, like “I am Alice from Acme”.
Signed URLA temporary link (about 15 minutes) that lets the browser put a file directly into the warehouse. The user never sees the secret password.
Secret / credentialThe warehouse password (AWS key, Azure key, etc.). It stays on the server only.

The same upload button works for every warehouse. Only the admin chooses “this customer uses AWS” or “this customer uses MinIO”.

Part A — One-time setup on your Windows PC

Step 1 — Install the tools once per computer

Install these three things. Accept the defaults.

  1. Node.js LTS from https://nodejs.org (the big green LTS button). After install, open a new PowerShell and type node -v. You should see something like v20.x.x.
  2. Docker Desktop from https://www.docker.com/products/docker-desktop/. Start it and wait until the whale icon in the system tray is steady. Leave “Linux containers” selected.
  3. Git from https://git-scm.com if you do not already have it.
You do not need an Amazon, Google, or Azure account to practise. Local MinIO is enough. Add AWS later in Step 8.
Step 2 — Open the project and create a settings file

In PowerShell:

cd C:\path\to\doc
copy .env.example .env
notepad .env

Leave the file as-is for local practice. The important lines are:

LineWhat it does
AUTH_DISABLED=trueSkips real login. You identify yourself with simple headers. Perfect for learning.
MYSQL_*Where the metadata database lives (names and sizes of files, not the files themselves).
MINIO_ACCESS_KEY=minioadminLocal warehouse username.
MINIO_SECRET_KEY=minioadminLocal warehouse password.

Save and close Notepad.

Step 3 — Start the database and the local warehouse
docker compose up -d

Wait 20–30 seconds. Check:

docker compose ps

You want mysql and minio listed as running.

  • MinIO website (the warehouse console): http://localhost:9001
  • Login: username minioadmin / password minioadmin

You do not have to create a bucket by hand. The DMS can create documents on first upload. If you prefer, in the MinIO console click Buckets → Create Bucket and name it documents.

If PowerShell says docker-compose is not found, try the older name: docker-compose up -d (with a hyphen).
Step 4 — Create the tables (the filing index)

The files themselves will live in MinIO/S3. MySQL only stores “this PDF belongs to Acme, it is version 2, it sits in folder Contracts”.

First time Docker created the database, it may already have run sql/schema.sql. To be safe, run both files:

Get-Content sql\schema.sql | docker compose exec -T mysql mysql -uroot -proot
Get-Content sql\seed.sql   | docker compose exec -T mysql mysql -uroot -proot

What you just created:

TableIn human language
tenantsList of customers
storage_configsWhich warehouse each customer uses, and the names of the secret env vars (not the secrets)
foldersFolders inside a customer
documentsEach file’s name, size, type, and where the bytes live
document_versionsOld copies of the same file
document_permissionsWho may read / write / delete a file
audit_logsA diary of who did what

seed.sql also inserts a practice customer:

  • Name: Acme Demo
  • Tenant id: 11111111-1111-1111-1111-111111111111
  • Warehouse: local MinIO, bucket documents

You can skip creating a tenant in Step 6 and jump to uploads using this id. Or create a second tenant to practise the full admin path.

Step 5 — Install Node packages and start the DMS
npm install
npm test
npm run serve:express-dev

Leave this window open. You should see a log that the server started.

Open a browser:

AddressWhat you see
http://localhost:3000/api/healthShould say "status":"ok" and list providers s3, minio, gcp, azure, fake
http://localhost:3000/api-docsSwagger — clickable forms for every API
If port 3000 is already used, change PORT=3001 in .env and restart.

Part B — How the system knows who you are

Because AUTH_DISABLED=true, you do not need a real login system yet. Every request must still say who you are and which company you belong to, using headers.

HeaderAdmin (you, setting up customers)Normal employee of Acme
x-tenant-idThe tenant you are working on (or bootstrap only when creating the first tenant)That company’s tenant id
x-user-ide.g. admin-1e.g. alice
x-user-namee.g. Platform Admine.g. Alice Kumar
x-rolesplatform_admin to create tenants;
tenant_admin to attach storage		empty, or tenant_admin for the customer’s own admin
In production you turn AUTH_DISABLED=false, set JWT_SECRET, and users send a login token in the idtoken header. The token must contain sub (user id), a name, and tenant_id. The rest of this guide stays the same.

In PowerShell, to avoid typing headers every time, you can set variables (do this in the second PowerShell window — not the one running the server):

$base = "http://localhost:3000/api"
$tenant = "11111111-1111-1111-1111-111111111111"

# Admin identity
$admin = @{
  "content-type" = "application/json"
  "x-tenant-id"  = $tenant
  "x-user-id"    = "admin-1"
  "x-user-name"  = "Platform Admin"
  "x-roles"      = "platform_admin,tenant_admin"
}

# Later: a normal Acme employee
$user = @{
  "content-type" = "application/json"
  "x-tenant-id"  = $tenant
  "x-user-id"    = "alice"
  "x-user-name"  = "Alice Kumar"
  "x-roles"      = "tenant_admin"
}
Use curl.exe in PowerShell, not curl. Plain curl is a different Windows command and will confuse you.

Part C — Admin: register a tenant and attach a warehouse

Step 6 — Create a customer (tenant) platform admin

Skip this if you are happy using the seeded Acme tenant. To practise the real onboarding:

curl.exe -s -X POST "$base/tenants" -H "content-type: application/json" `
  -H "x-tenant-id: bootstrap" `
  -H "x-user-id: admin-1" `
  -H "x-roles: platform_admin" `
  -d "{`"name`":`"Acme Corp`",`"slug`":`"acme-corp`",`"maxFileSizeBytes`":52428800}"

You get JSON back. Copy tenant.id — a long id like 3f2c..... That id is the customer’s permanent number. Put it in $tenant:

$tenant = "PASTE-THE-ID-HERE"
$admin["x-tenant-id"] = $tenant
$user["x-tenant-id"]  = $tenant

What each field meant:

FieldMeaning
nameDisplay name, any words
slugShort computer name, lowercase, no spaces. Must be unique.
maxFileSizeBytesLargest file this customer may upload. 52428800 = 50 MB.

Only a user with role platform_admin (or admin) can create tenants.

Step 7 — Put warehouse passwords on the computer admin / IT, never the end user

The database is not allowed to store the real AWS/Azure/Google password. It only stores the name of an environment variable. You put the real value on the machine that runs the DMS.

For local MinIO (already done if you copied .env.example):

MINIO_ACCESS_KEY=minioadmin
MINIO_SECRET_KEY=minioadmin

For a real AWS customer named Acme, create an IAM user that can only touch Acme’s bucket, then on the server:

# PowerShell — user-level env (open a NEW terminal after this)
setx TENANT_ACME_ACCESS_KEY "AKIA................"
setx TENANT_ACME_SECRET_KEY "wJal................"

Or add the same two lines to .env and restart npm run serve:express-dev.

Same idea for other vendors:

VendorWhat you set on the server
AWS S3TENANT_ACME_ACCESS_KEY and TENANT_ACME_SECRET_KEY (IAM access key + secret)
MinIOaccess key + secret key (local demo: minioadmin / minioadmin)
Google CloudTENANT_ACME_GCP_SA = full path to the service-account JSON file, e.g. C:\secure\acme.json
Azure BlobTENANT_ACME_AZURE_KEY = storage account key; you also send the account name (not secret) in the API
Never paste AKIA... or the Azure key into the API body. Never commit .env to Git. The API only accepts the name of the variable.
Step 8 — Attach the warehouse to the tenant tenant_admin or platform_admin

This is the only place the vendor is chosen. After this, every upload API is identical.

8a. Local practice — MinIO (do this first)

curl.exe -s -X PUT "$base/tenants/$tenant/storage" `
  -H "content-type: application/json" `
  -H "x-tenant-id: $tenant" `
  -H "x-user-id: admin-1" `
  -H "x-roles: tenant_admin" `
  -d "{
    `"provider`": `"minio`",
    `"container`": `"documents`",
    `"endpoint`": `"http://127.0.0.1:9000`",
    `"region`": `"us-east-1`",
    `"accessKeyRef`": `"MINIO_ACCESS_KEY`",
    `"secretKeyRef`": `"MINIO_SECRET_KEY`",
    `"useSsl`": false,
    `"basePrefix`": `"dms`",
    `"signedUrlTtlSeconds`": 900
  }"

You should get the same fields back. accessKeyRef is still a name, not minioadmin.

8b. AWS S3 (when the customer is ready for Amazon)

In AWS console: create a bucket (example acme-documents) in a region (example ap-south-1). Create an IAM user with permission to that bucket only. Put the keys in env as in Step 7. Then:

curl.exe -s -X PUT "$base/tenants/$tenant/storage" `
  -H "content-type: application/json" `
  -H "x-tenant-id: $tenant" `
  -H "x-user-id: admin-1" `
  -H "x-roles: tenant_admin" `
  -d "{
    `"provider`": `"s3`",
    `"container`": `"acme-documents`",
    `"region`": `"ap-south-1`",
    `"accessKeyRef`": `"TENANT_ACME_ACCESS_KEY`",
    `"secretKeyRef`": `"TENANT_ACME_SECRET_KEY`",
    `"basePrefix`": `"dms`",
    `"signedUrlTtlSeconds`": 900
  }"

If a web browser will upload directly to S3, add a CORS rule on the bucket allowing PUT/GET from your website. That is an AWS console setting, not a DMS setting.

8c. Google Cloud Storage

{
  "provider": "gcp",
  "container": "acme-documents",
  "projectId": "acme-prod",
  "credentialsJsonRef": "TENANT_ACME_GCP_SA"
}

8d. Azure Blob Storage

{
  "provider": "azure",
  "container": "acme-documents",
  "accountName": "acmeprod",
  "secretKeyRef": "TENANT_ACME_AZURE_KEY"
}

You can change the vendor later with the same PUT. New uploads go to the new warehouse. Old files stay where they were until you migrate them.

Step 9 — Confirm the tenant is ready
curl.exe -s "$base/tenants/me" `
  -H "x-tenant-id: $tenant" `
  -H "x-user-id: admin-1" `
  -H "x-roles: tenant_admin"

You should see the tenant name and a storage object with provider and container. If storage is null, Step 8 did not save. If you see a storage error later, the env var name in Step 8 does not match a real variable on the machine — restart the Node process after editing .env.

Part D — How a tenant user uses the product

From here on you are Alice, an employee of Acme. Use the $user headers. The APIs below do not mention S3 or MinIO. The server already knows.

Step 10 — Create a folder (optional)
curl.exe -s -X POST "$base/folders" -Headers $user `
  -d "{`"name`":`"Contracts`"}"

PowerShell’s curl.exe does not take -Headers $user like that. Use this reliable form:

curl.exe -s -X POST "$base/folders" `
  -H "content-type: application/json" `
  -H "x-tenant-id: $tenant" `
  -H "x-user-id: alice" `
  -H "x-user-name: Alice Kumar" `
  -H "x-roles: tenant_admin" `
  -d "{`"name`":`"Contracts`"}"

Copy folder.id if you want files to go inside that folder. You can nest folders by sending "parentId":"THE-PARENT-FOLDER-ID".

List folders:

curl.exe -s "$base/folders" `
  -H "x-tenant-id: $tenant" -H "x-user-id: alice" -H "x-roles: tenant_admin"

Rename: PATCH /api/folders/{id} with {"name":"Legal"}. Delete: DELETE /api/folders/{id} (soft delete).

Step 11 — Upload a small file through the API easiest first success

The file travels: your PC → DMS → warehouse. Fine for a few megabytes. Not ideal for a 500 MB video.

Create a sample file, then upload it:

"Hello from Acme" | Out-File -Encoding utf8 .\hello.txt

curl.exe -s -X POST "$base/documents" `
  -H "x-tenant-id: $tenant" `
  -H "x-user-id: alice" `
  -H "x-user-name: Alice Kumar" `
  -H "x-roles: tenant_admin" `
  -F "file=@hello.txt" `
  -F "filename=hello.txt" `
  -F "name=Welcome note"

To put it in the folder from Step 10, add -F "folderId=PASTE-FOLDER-ID".

Successful answer looks like:

{
  "document": {
    "id": "........-....-....-....-............",
    "name": "Welcome note",
    "originalFilename": "hello.txt",
    "status": "active",
    "storageProvider": "minio",
    "storageContainer": "documents",
    "storageKey": "dms/11111111-.../......../v1/hello.txt",
    "currentVersion": 1
  }
}

Copy document.id. That is the file’s id for every later call.

If this works, the whole chain is healthy: identity → tenant → warehouse credentials → MinIO/S3 → MySQL metadata.
Step 12 — Upload a large file the proper way (signed URL) production path

The file goes: your PC → warehouse. The DMS only writes the index card, then later checks that the box arrived.

12.1 Ask for an upload session

curl.exe -s -X POST "$base/documents" `
  -H "content-type: application/json" `
  -H "x-tenant-id: $tenant" `
  -H "x-user-id: alice" `
  -H "x-roles: tenant_admin" `
  -H "idempotency-key: invoice-2026-08-19" `
  -d "{
    `"filename`": `"invoice.pdf`",
    `"mimeType`": `"application/pdf`",
    `"name`": `"August invoice`",
    `"size`": 123456
  }"

You get two important things:

  • document.id — the index card (status is pending_upload until step 12.3)
  • upload.url — a temporary warehouse door. Method is PUT. It expires at upload.expiresAt.

Save them:

$docId = "PASTE-DOCUMENT-ID"
$uploadUrl = "PASTE-THE-LONG-URL"

The idempotency-key header means “if the network blips and I send this twice, do not create two documents”. Same key → same document.

12.2 PUT the real file at that URL

This call goes to MinIO or S3, not to localhost:3000.

curl.exe -s -X PUT "$uploadUrl" `
  -H "Content-Type: application/pdf" `
  --data-binary "@C:\Users\Public\invoice.pdf"

If you used a text file while practising:

curl.exe -s -X PUT "$uploadUrl" `
  -H "Content-Type: text/plain" `
  --data-binary "@hello.txt"

A successful PUT is usually empty with HTTP 200. If the URL expired, go back to 12.1.

12.3 Tell the DMS “the box has arrived”

curl.exe -s -X POST "$base/documents/$docId/upload" `
  -H "content-type: application/json" `
  -H "x-tenant-id: $tenant" `
  -H "x-user-id: alice" `
  -H "x-roles: tenant_admin" `
  -d "{}"

The DMS checks the warehouse. If the object is there, status becomes active and version 1 is recorded. If you forgot 12.2, you get an error that the upload has not reached storage — PUT the file and call this again. It is safe to retry.

Step 13 — Find the file, see details, download it

13.1 List this tenant’s documents

curl.exe -s "$base/documents" `
  -H "x-tenant-id: $tenant" -H "x-user-id: alice" -H "x-roles: tenant_admin"

Optional query words you can add to the URL:

QueryExampleMeaning
q?q=invoiceSearch by name
folderId?folderId=...Only that folder
includeDeleted?includeDeleted=trueAlso show recycle-bin files
limit / offset?limit=20&offset=0Paging

13.2 Get one document

curl.exe -s "$base/documents/$docId" `
  -H "x-tenant-id: $tenant" -H "x-user-id: alice" -H "x-roles: tenant_admin"

13.3 Metadata (index card + warehouse object info)

curl.exe -s "$base/documents/$docId/metadata" `
  -H "x-tenant-id: $tenant" -H "x-user-id: alice" -H "x-roles: tenant_admin"

13.4 Download — preferred (signed URL)

curl.exe -s -X POST "$base/documents/$docId/download" `
  -H "content-type: application/json" `
  -H "x-tenant-id: $tenant" -H "x-user-id: alice" -H "x-roles: tenant_admin"

Open download.url in a browser, or:

curl.exe -L "PASTE-DOWNLOAD-URL" -o downloaded.pdf

13.5 Download — fallback (file streams through the DMS)

curl.exe -L "$base/documents/$docId/content" `
  -H "x-tenant-id: $tenant" -H "x-user-id: alice" -H "x-roles: tenant_admin" `
  -o downloaded.txt

13.6 Rename or move

curl.exe -s -X PATCH "$base/documents/$docId" `
  -H "content-type: application/json" `
  -H "x-tenant-id: $tenant" -H "x-user-id: alice" -H "x-roles: tenant_admin" `
  -d "{`"name`":`"August invoice (signed)`", `"folderId`": null}"
Step 14 — Upload a new version of the same document

The product keeps version 1, 2, 3… itself. It does not depend on S3 versioning.

Small file:

curl.exe -s -X POST "$base/documents/$docId/versions" `
  -H "x-tenant-id: $tenant" -H "x-user-id: alice" -H "x-roles: tenant_admin" `
  -F "file=@hello.txt" -F "filename=hello.txt"

Large file (same 3-step dance as Step 12):

curl.exe -s -X POST "$base/documents/$docId/versions" `
  -H "content-type: application/json" `
  -H "x-tenant-id: $tenant" -H "x-user-id: alice" -H "x-roles: tenant_admin" `
  -d "{`"filename`": `"invoice.pdf`", `"mimeType`": `"application/pdf`"}"
# then PUT the file to the new upload.url
# then POST /api/documents/$docId/upload

List versions:

curl.exe -s "$base/documents/$docId/versions" `
  -H "x-tenant-id: $tenant" -H "x-user-id: alice" -H "x-roles: tenant_admin"

Download an old version by adding ?versionNumber=1 to the download or content URL.

Step 15 — Share the document with a colleague

The uploader is already the owner (full rights). To let Bob only read:

curl.exe -s -X POST "$base/documents/$docId/permissions" `
  -H "content-type: application/json" `
  -H "x-tenant-id: $tenant" -H "x-user-id: alice" -H "x-roles: tenant_admin" `
  -d "{
    `"principalType`": `"user`",
    `"principalId`": `"bob`",
    `"canRead`": true,
    `"canWrite`": false,
    `"canDelete`": false,
    `"canAdmin`": false
  }"

List grants: GET /api/documents/{id}/permissions. Remove one: DELETE /api/documents/{id}/permissions/{permissionId}.

If Bob then calls GET with x-user-id: bob and no extra roles, he can read. He cannot delete. A user from another tenant can never see this id at all.

Step 16 — Delete, restore, erase

Put in the recycle bin (file stays in the warehouse):

curl.exe -s -X DELETE "$base/documents/$docId" `
  -H "x-tenant-id: $tenant" -H "x-user-id: alice" -H "x-roles: tenant_admin"

Bring it back:

curl.exe -s -X POST "$base/documents/$docId/restore" `
  -H "x-tenant-id: $tenant" -H "x-user-id: alice" -H "x-roles: tenant_admin"

Erase the warehouse object as well:

curl.exe -s -X DELETE "$base/documents/${docId}?permanent=true" `
  -H "x-tenant-id: $tenant" -H "x-user-id: alice" -H "x-roles: tenant_admin"

Part E — Same story in Swagger (mouse instead of curl)

  1. Open http://localhost:3000/api-docs.
  2. Because AUTH_DISABLED=true, Swagger’s lock icon is not enough by itself. Use an API client (Postman) or still send the x-tenant-id / x-user-id / x-roles headers. In Swagger you can often add them if you use “Try it out” after configuring the two apiKey schemes, but the easiest learning path on Windows is Postman:
    • New request → Headers: the four x-* headers
    • Body → form-data → key file type File → select a file → POST http://localhost:3000/api/documents
  3. Order of clicks for a new customer:
    1. POST /tenants
    2. PUT /tenants/{id}/storage
    3. GET /tenants/me
    4. POST /folders (optional)
    5. POST /documents (JSON for signed URL, or multipart for a small file)
    6. If JSON: PUT the file to upload.url, then POST /documents/{id}/upload
    7. POST /documents/{id}/download

Part H — Security rules to remember

  • End users never receive AWS / Azure / Google passwords.
  • They only receive a signed URL that dies in about 15 minutes.
  • One tenant cannot read another tenant’s document, even if they guess the UUID.
  • The owner of a file (the x-user-id who created it) and tenant_admin can always access it. Everyone else needs a permission row.
  • Do not put real keys in Git, in Slack, or in the storage_configs table.
